### 阶段 4 实施记录（2026-10-10）

落地形态：

- 存储：`data/state/views.json`，`{ "<albumId>": { path, file, updatedAt } }`；
  **有界**（条数 = 专辑数），删专辑时顺手清掉，启动时也清一次"专辑已不存在"的孤儿条目
- 界面：点专辑 → 优先回到该专辑上次浏览的目录（没有记录就用专辑根目录）；
  一次列目录成功后就上报（800ms 节流，连续翻目录只写最后一次）
- 容错：上次那个目录已被删/改名时，自动退回专辑根目录 + 提示，并清掉那条记录
- **「上次」标记**：最近播放过的文件在它所在目录里带一个 `上次` 小标记
  （播放时服务端记 `file`，界面本地也立刻更新，不用等下一次拉取）
- 接口：`GET /api/views`、`PUT /api/views/<albumId>`（只传 path 或只传 file 都是**合并**语义）；
  `/api/state` 会带上 `views`

顺带修掉一个竞态：`POST /api/play` 的响应里，IPC 模式下播放列表要等 mpv 的 playlist 事件才填充，
连播时响应会短暂只有 1 项；现在 replace 时立刻按"刚交给 mpv 的列表"填充，响应内容两种模式一致。

测试：`state-test` 增至 35 项（views 读写/合并/删专辑清理/孤儿清理/坏文件容错）；
e2e 增至 117 项（记录浏览位置、播放后记文件、连播响应里的列表形状）；ui-test 增至 54 项
（重新点专辑回到上次目录、最近播放那集带「上次」标记）

### 阶段 3 实施记录（2026-10-10）

落地形态：

- **默认**：双击一行 / 选中后回车 = **从这一集开始连播本目录剩余**（`POST /api/play {mode:'series'}`）
- **⋯ 菜单**：从此集开始连播 / 只播这一集（`single`）/ ↺ 从头播放 / ＋ 追加到播放列表 / 复制路径 / 复制名称
- **规则**：同目录 + 同类型（视频配视频、音频配音频）+ **自然排序**（自己实现的比较器：数字段按数值比，
  `第2集` 在 `第10集` 前；文本段走 `localeCompare('zh')`）
- **交给 mpv**：整段列表一次性 `loadfile`（第一条 replace、其余 append），**点的那一集就是第一条**
  —— 不会出现"先闪一下第 1 集"的跳变；之后的"下一集"由 mpv 自己推进，网页不再同步队列
- **每集各自挂字幕**：目录只列**一次**（parent + 字幕子目录），每集字幕本地匹配后各自挂上
  （为此把原来的 `discoverSubtitles` 拆成 `subtitleContext`（联网一次）+ `subtitlesFor`（纯计算））
- **不落盘**：播放列表与"看到第几集"都不由我们保存（mpv 自己管播放列表；进度仍按流地址记）
- 与计划的差异：没有做"整个目录连播"（含前面的集）—— 那需要额外的 `playlist-pos` 跳转与状态处理，
  而"从这集开始"是选定的默认行为，"只播这一集"也已在菜单里，够用了

测试：新增 `tools/series-test.js`（自然排序 + 连播列表组装，15 项，已进 CI）；
e2e 增至 114 项（连播范围 / 列表形状 / 当前集 / 每集字幕 / mpv 自己推进到下一集）；
ui-test 增至 52 项（真实双击一集 → 自动连播本目录剩余）

### 阶段 2 实施记录（2026-10-09）

实测结论（决定了实现细节）：

| 实验 | 结果 |
| --- | --- |
| http 流地址能否记录+续播 | 能：条目名 = `MD5(URL)`，再次播放自动从上次位置开始 ✅ |
| 切换文件（`loadfile replace`）时，上一个文件 | **不会**自动保存 → 我们必须在切集前主动发一次 `write-watch-later-config` |
| `--resume-playback-check-mtime` | http 地址没有 mtime，用不上（同路径换文件的场景需手动「从头播放」） |
| 停止 / 关窗口 / 退出 | mpv 自动保存 ✅ |
| 播到结尾 | 不保存（=看完）✅ |
| 同文件重载 + 「从头播放」 | mpv 会先把旧位置写回条目 → 除了删条目，还要显式传 `start=0`（实测能压过 watch-later） |

落地内容：

- 新增 `server/watchlater.js`：md5 键、读/写/删、扫描、LRU 清理（条数 + 天数）、URL ↔ 专辑/文件解析、旧进度迁移
- `server/mpv.js`：`--watch-later-directory=<data>/cache/watch-later`、`--watch-later-options=start`、`--save-position-on-quit=yes`；新增 `savePosition()`，在**切集前 / 停止时 / 退出时**主动保存
- `server/index.js`：删掉自管进度状态机（节流写盘、阈值判定、记录匹配）与 `server/resume.js`；`/api/resume` 改为读 mpv 条目；启动时迁移旧快照 + 清理一次，之后每天一次；`DELETE /api/resume` 只清最近一条
- 前端：设置里新增进度条数/天数上限与「立即清理一次」；「继续观看」按钮改为读 mpv 的条目
- 测试：`resume-test` 重写为 watchlater 单测（31 项）、`state-test` 26 项、e2e 98 项（IPC）、ui-test 45 项

## 0. 结论速览

| 议题 | 结论 |
| --- | --- |
| 进度记忆 | **改用 mpv 原生的 watch-later**（实测能自动续播），本应用只"读 + 清理"，**删掉自管的进度状态机** —— 这是治"各种条件下不一致"的根本办法 |
| 剧集连播 | **一次性把整段剧集交给 mpv**，之后由 mpv 自己推进"下一集"；我们不再逐集 append / 同步 |
| 专辑最后目录 | 一个按专辑索引的小 JSON（有界），与进度无关 |
| 存储 | **不需要 SQLite**（Node 24 虽自带 `node:sqlite` 且零依赖）；改为 `data/` 三分区：配置 / 状态 / 缓存，每类都有界并写明"能不能删" |
| 前置条件 | **把流代理 URL 固定下来**（token 持久化 + 端口固定），否则 mpv 的进度键每次都变 |

| 实验 | 做法 | 结果 |
| --- | --- | --- |

| C | 播 3 秒后发 `stop`（不显式保存），随后 `quit` | 仍写出 `start=3.023000` → **"停止"按钮也会保存** ✅ |

## 2. mpv 原生能记什么、不能记什么

**能记**：单个文件的播放位置；可选地记住音量/音轨/字幕轨/延迟/画面比例等 50+ 项（我们只保留 `start`）；播放列表里"某一项有进度就从那一项续起"（mpv 手册语义）。

**不能记**：最近播放列表、"上次浏览到哪个目录"、跨设备同步、"最近看过哪几部"。→ 这些必须我们自己存，但都很小、有界。

## 3. 目标架构：让 mpv 当唯一真相源

```
网页(UI 呈现)  ──HTTP/SSE──►  Node 服务  ──命名管道 IPC──►  mpv
    ▲                            │                          │
    │                            ├─ 组装播放列表（剧集）        ├─ 播放（GPU 渲染）
    └──── 进度/状态(只读) ◄───────┤                          ├─ 写 watch-later（进度）
                                 └─ 读 watch-later 供 UI 显示   └─ 自行推进"下一集"
```

四条规则（针对"交互和同步很烦"）：

1. **意图一次性下达**：要播哪一集、从哪开始、整段列表是什么 —— 一次说完，后续交给 mpv。
2. **进度只由 mpv 写**，我们只读；不再有"我们判断何时该保存"的逻辑。
3. **播放状态只由 mpv 给**（`observe_property`），我们不做镜像队列状态机。
4. **能重建的一律不落盘**：播放列表、播放状态都不存；只有"每个专辑最后浏览的目录"这种无法重建的才存。

## 4. 三项需求的设计

### 4.1 进度：改用 mpv 原生

**启动参数改动**

| 现在 | 改为 |
| --- | --- |
| `--no-save-position-on-quit`（禁止写） | 去掉，改 `--watch-later-directory=<data>/cache/watch-later` + `--save-position-on-quit=yes` |
| `--no-resume-playback`（禁止读） | 去掉（默认 `resume-playback=yes`） |
| `--watch-later-options` 默认 50+ 项 | `--watch-later-options=start`（只记进度） |
| 另加 | `--write-filename-in-watch-later-config=yes`（便于索引与清理） |

> 与"外部直接用 mpv 打开文件"的隔离**依然成立**：只是从"禁用"变成"重定向到我们自己的目录"，两边互不读写。

**URL 稳定化（前置条件）**

- `data/state/instance.json` 存一次性生成的 stream token（重启不再变）
- 端口固定（默认 8787）；若端口被占用则提示用户，而不是悄悄换端口（否则进度键变化、旧进度失联）
- README 里写明：**换端口/删 instance.json 会让已有进度失联**（可接受，属于可预期行为）

**保存时机**（全部交给 mpv，我们只在两处兜底）

| 场景 | 谁来保存 |
| --- | --- |
| 关 mpv 窗口 / 按 q / 应用退出 | mpv 自动（实测 C、D） |
| 点网页「停止」 | mpv 自动（实测 C：stop 时也写） |
| 切到另一集 / 另一个文件 | 我们发一次 `write-watch-later-config`（兜底，避免 mpv 实现差异） |
| 播到结尾 | 不写（=看完，符合直觉） |

**UI 上的「继续观看」**

- 主数据：直接读 `cache/watch-later/` 里对应条目（我们算 `MD5(URL)`，实测已验证命名规则）
- 另存 `data/state/recent.json`：**仅为显示**"哪个专辑、哪个文件、看到几分几秒"（1 条）。它 **丢失/删掉都不影响续播**——播放由 mpv 决定。
- 这样"显示"和"播放"解耦：显示错了不会导致放错，这也正是现在"不一致"的根源（我们的记录同时承担了显示与播放决策）。

**清理**（防膨胀，必须做）

- 条目上限（默认 200，可调）+ 未访问天数上限（默认 90 天）
- 顺带删除孤立的 redirect 条目
- 清理时机：服务启动后延迟执行一次 + 每天一次；不阻塞播放
- 设置里给两个滑块/输入框；README 写明"整个 `data/cache/` 可以随手删"

**下线的代码**：`server/resume.js` 的 tracker/阈值判定、`data/last-played.json`（迁移到 `state/recent.json`）。

> 代价（诚实说）：token 持久化后 URL 可预测（仍只监听 127.0.0.1，风险很低）；端口不能随意改；`cache/watch-later` 里会有小文件（已用上限治理）。

### 4.2 剧集连播（PotPlayer 式）

- **默认行为**：双击某一集 = **从这一集开始，连播本目录剩余剧集**
- 行内菜单提供：`只播这一集` / `从这集连播本目录` / `整个目录连播` / `追加到播放列表`
- 服务端收单：`POST /api/play { mode: 'series'|'single'|'append', startIndex, path }`
  - 服务端一次性组装 items（含各自的字幕）→ IPC 下第一条 `loadfile replace`、其余 `loadfile append`，再 `playlist-pos=startIndex`
  - 无需临时播放列表文件（mpv 另有 `loadlist` 命令，但会落临时文件，**不采用**）
- **分组规则（默认）**：同目录 + 视频类型 + **自然排序**（`第2集` 排在 `第10集` 前）
  - 进阶（可选，第二阶段）：按 `第xx集 / EPxx / SxxExx` 识别剧号分组，处理"一个目录混多季"
- **退出后再看**：点「继续观看」→ 因为我们一次性把整段列表交给 mpv，且上次那集有进度，**mpv 会自动跳回那一集**（mpv 手册语义）——正好是 PotPlayer 的体验，零额外代码
- **不落盘**：播放列表与"看到第几集"都不由我们存

### 4.3 专辑最后目录

- 文件：`data/state/views.json`
- 结构：`{ "<albumId>": { "path": "/影视/剧集/穹庐下的魔女", "file": "/影视/剧集/…第03集.mp4", "updatedAt": 1791… } }`
- 行为：点开专辑 → 直接恢复到该目录；该目录里把最后播放的文件高亮（可选）
- 有界：条数 = 专辑数（几十），体积几 KB；专辑删除时顺手清掉对应条目

## 5. `data/` 目录规划（回答"会不会越来越乱"）

```
data/
├─ albums.json              配置：专辑（含明文密码）        ← 要备份，别手改坏
├─ settings.json            配置：设置                      ← 要备份
├─ albums.json.bak          配置备份（已有机制）
├─ settings.json.bak
├─ state/                   状态：丢了可重建，体积有界
│   ├─ views.json           每个专辑最后浏览目录 + 最后播放文件
│   ├─ recent.json          仅用于界面显示的"最近进度"（1 条）
│   └─ instance.json        stream token（固定值，保证进度键稳定）
└─ cache/                   缓存：随时可整目录删除
    └─ watch-later/         mpv 原生进度（受上限清理）
```

| 类别 | 能不能删 | 上限与清理 |
| --- | --- | --- |
| 配置（albums/settings） | **不能**（删了要重建专辑） | 有 `.bak` 自动备份 |
| 状态（state/） | 能删（会丢"最后目录/继续观看"提示） | 条数由专辑数/1 条界定 |
| 缓存（cache/） | 随便删 | 条目数 + 天数上限，自动 LRU 清理 |

**硬规则（写进 CONTRIBUTING/README）**：任何新功能要落盘，必须归入三类之一，并在文档里写明**它在哪、多大、怎么被清理**；不允许在 `data/` 根目录新增零散文件。

**迁移**：读取旧 `data/last-played.json` → 写入 `state/recent.json` → **删除旧文件**（一次性完成，之后不再产生）。

## 6. 要不要动 SQLite？

| 方案 | 适用 | 成本 |
| --- | --- | --- |
| 现状 JSON（+ 分区） | 配置 < 100 条、状态 < 几百条、缓存交给 mpv | 全量重写，但文件很小（几十 KB～几百 KB） |
| **分片 JSON**（按专辑一个文件） | 若状态条目增长到几千条 | 略复杂，但仍是纯文本、可手工备份 |
| SQLite（`node:sqlite`，零依赖） | 条目 > 5 万 / 需要多条件查询统计 / 并发写 / 频繁增量写 | schema + 迁移 + 可读性下降 |

**结论：现在不需要 SQLite。** 采用 mpv 原生进度后，"会增长的数据"就只有 watch-later 目录（交给 mpv 的文件格式 + 我们的 LRU 清理），根本不需要数据库。
将来若要做「全库观看历史 + 统计 + 跨设备同步」，再上 `node:sqlite`（单文件，反而符合"不散落小文件"的诉求）。

2. 若用原生：接受 **token 持久化 + 端口固定**（换端口会丢已有进度）吗？
3. 进度保留策略：mpv 默认是**每个文件一条**（配 LRU 上限清理）——可接受吗？还是希望只保留"最近 N 条"？
4. 连播默认：双击一集 → **从这集连播本目录剩余**（推荐）/ 只播这一集 / 每次询问
5. 剧集分组：**整个目录自然排序**（简单、推荐）还是按集号前缀分组（复杂、更贴近命名混乱的库）
6. 存储：**JSON 三分区**（推荐）还是 SQLite
7. 阶段 0（data/ 重构 + 迁移）现在就做吗？—— 它没有行为变化，能先把"乱"止住
